# Risks, constraints and mitigations (deliverable L)

Likelihood (L) and impact (I) are rated H/M/L. Ordered roughly by L × I.

| # | Risk | L | I | Mitigation in place | Residual / what you should do |
|---|---|---|---|---|---|
| 1 | **Agent misuse: prompt injection triggers refunds, cancellations or money routing** | M | H | Live mutations are double-gated (`PAYMENTS_ALLOW_LIVE_MUTATIONS` + `confirm`; Skydo and Infinity receipts in sandbox too). `provider_options` cannot set splits, transfers, connected accounts, manual capture or redirect URLs (baseline + per-gateway lists, payments and subscriptions). `destructiveHint` annotations. Tool descriptions demand human approval. Audit log records `blocked` attempts. `refund_ref` idempotency. Refunds bounded by the refundable balance | `confirm` can be set by the agent itself. Rely on MCP-client approval prompts. Never give an agent that reads untrusted text live refund rights. See [security.md §8](security.md#8-threat-model-for-agents) |
| 2 | **Gateway API drift** (field renames, new API versions, host moves) | H | M | Plain fetch with per-adapter contract tests. Pinned versions where the gateway supports it (Cashfree `x-api-version: 2026-01-01`, Stripe `2025-03-31.basil`; Dodo has no version header, so its adapter follows spec 1.120.26 unpinned). `lastVerified` date per capability map. `raw` passthrough. `api_drift` issue template | Drift appears as `PROVIDER_ERROR` / `SIGNATURE_INVALID` in production before tests catch it. Run a sandbox smoke test before upgrading, and monitor error rates per gateway |
| 3 | **Unverified CCAvenue details** (encryption kit, `orderStatusTracker` / `refundOrder` fields, API version 1.1 vs 1.2, no signed webhooks) | H | M | Marked `partial` / UNVERIFIED in capabilities and docs. Callbacks verified by decryption plus amount/order checks. Refunds never auto-retried | Test every CCAvenue flow in its sandbox. Confirm the kit (CBC vs GCM) with CCAvenue. Re-check status before fulfilling. Contributions with the official PDF are wanted |
| 4 | **Weakly authenticated webhooks** (PhonePe static auth header, CCAvenue decryption-only) | M | H | Both marked `partial`. `createWebhookHandler` re-checks status and dedupes on the confirmed data, not the body's id | If you call `parseWebhook` yourself, implement the re-check. The status API is the source of truth |
| 5 | **Per-process state** (idempotency store: create 10 min, refunds 24 h; webhook dedupe; MCP HTTP sessions; mock ledger) | H (when scaling) | M | Pluggable `IdempotencyStore`, `WebhookDedupeStore`, `AuditSink` interfaces. Gateway-side de-dupe ids where available. After `OUTCOME_UNKNOWN` or a duplicate rejection, refunds are looked up by `refund_ref` (not on PayU/CCAvenue) | Before running more than one replica, plug in Redis/Postgres stores, use sticky sessions for `/mcp`, or run one replica. PayU/CCAvenue refunds have no gateway-side de-dupe |
| 6 | **"valid" misread as "paid"** | M | H | `valid` uniformly means "authentic and matches the order"; PaymentsClient adds `paid` (valid + status `captured` or `partially_refunded` + the caller passed both `orderRef` and `expectedAmount`). `authorized` and fully `refunded` are not paid; Razorpay reports `captured` only when the order is fully paid. Docs say: fulfil only on `paid` | No capture API: with Razorpay manual capture or Stripe manual capture, orders never become `paid` here. Keep auto-capture on |
| 7 | **Stripe India is invite-only** | H | M | Capability summary and constraints say so. Recommender priors favour Stripe only for `international` | New Indian merchants generally can't onboard. Use Stripe as an exports adapter on existing accounts |
| 8 | **Skydo has no public API** | certain | M | The adapter never contacts Skydo. It automates Skydo's Zoho Books integration (create, status, verify are `partial`) or hands out receiving-account details with a local ledger. Everything else is `unsupported`. See [skydo.md](skydo.md) | Skydo's import of API-created Zoho invoices is not separately documented: confirm with one real invoice during setup. Ledger mode depends on a human recording receipts correctly (gated in sandbox and live; receipt ids unique across orders) and on a local disk for the file lock. Switch to Skydo's API when it ships |
| 9 | **Shopify limits**: Shopify Payments unavailable in India, payment extensions limited to approved partners | certain | M | Documented in the gateway matrix. Plugins listed per gateway | This project can't be a Shopify checkout. Use the gateway's Shopify app, and this server for status, refunds and recon |
| 10 | **Amount unit errors** (rupees vs paise, dollars vs cents) | M | H | Integer minor units only (paise for INR, cents for USD) (`assertMinorUnits`, zod `int().positive()`). Adapters convert at the boundary. The PayU hash is computed over the exact sent string. Cashfree's rupees-as-number is converted both ways | Callers who pass rupees get a 100× **smaller** charge, not an error, if the value is an integer. Name variables `amountPaise` in your code |
| 11 | **Live key used in sandbox, or vice versa** | M | H | Razorpay prefix checks. `doctor` / `check_config` surface `initError` | PayU and CCAvenue keys aren't distinguishable. Keep sandbox and live secrets in separate vaults and processes |
| 12 | **Paytm host rebrand** (`securegw.paytm.in` → `secure(stage).paytmpayments.com`, refund pages showing `securegw-stage.paytmpayments.in`) | M | M | Defaults to the new hosts, documented in constraints | Confirm hosts in sandbox. Override via adapter changes if Paytm moves again |
| 13 | **PayU refund status and webhook formats only partly documented** | M | L | `partial`, defensive parsing, refund webhooks not parsed | Poll refund status |
| 14 | **Regulatory change** (RBI e-mandate thresholds, PA-PG, tokenisation, cross-border rules) | M | M | No card data handled. Hosted checkouts only. Constraints document current e-mandate rules | Not legal advice. Track RBI circulars and gateway notices. Thresholds in docs (₹15,000, 24 h pre-debit) may change |
| 15 | **Gateway outage** | M | M | Safe retries on reads. Typed `PROVIDER_UNAVAILABLE`. Recommender for alternatives | Checkout-level failover is your call. See the reliability playbook |
| 16 | **HTTP transport exposure** | L | H | Bearer token ≥ 24 chars, constant-time compare, loopback default, exact `/mcp` path, validated port, idle sessions evicted after 30 min, max 1,000 sessions, non-root container | No TLS, rate limiting or per-user auth built in. Put it behind a proxy |
| 17 | **Supply chain** | L | H | Two runtime deps (`@modelcontextprotocol/sdk`, `zod`). No gateway SDKs. Lockfile + `npm ci` in CI | Pin versions. Run `npm audit` / Dependabot. Verify npm provenance when you publish |
| 18 | **Generated integration code quality** | M | M | Generator emits server-side secrets only and verify-before-fulfil patterns | Review generated code like any PR |
| 19 | **Trademark / affiliation confusion** | L | M | Disclaimer in README and docs. No logos. Dodo ships its own official MCP server (npm `dodopayments-mcp`); the docs describe this one as a separate cross-gateway server, not affiliated with Dodo | Don't present this as an official SDK of any gateway, or as "the" Dodo MCP |
| 20 | **Infinity has no public API, and its Zoho integration is undocumented** | certain | M | The adapter never contacts Infinity (its Terms forbid reverse engineering). Zoho Books bridge (paid only when Zoho payments cover the total), or receiving-account details and/or a QuickLink (https on `INFINITY_QUICKLINK_HOSTS` only) with a local ledger. Separate `INFINITY_ZOHO_*` variables so Skydo's Zoho setup never switches Infinity onto Zoho. Everything else is `unsupported`. See [infinity.md](infinity.md) | What Infinity's Zoho integration syncs is not publicly documented: confirm with one real invoice that Infinity marks it paid in Zoho, and never connect Skydo and Infinity to the same Zoho organisation. The code cannot check what a QuickLink charges. Card payments can be disputed after you record them. Ledger mode depends on a human recording receipts from the Infinity dashboard (gated in sandbox and live). Ask support@infinityapp.in about API access |
| 21 | **Dodo Payments: products first, customer-made payments carrying your order ref, no idempotency key, never run against Dodo's test mode** | H | M | The adapter charges only a product that exists in Dodo and checks before the POST that its price is exactly `amount` (no discount, PPP or localized prices) or that it is pay-what-you-want. Sessions turn off discount codes and currency selection. Verify requires the stored `cks_` session id and accepts only that session's payment, then checks order ref, price (or price plus the tax Dodo added) and currency; status and webhooks report another currency as `unknown`; the generated webhook handler ignores events for another session or currency. Status and refunds refuse payments not created by this library. POSTs are never retried; refunds look for an existing `refund_ref` first. Standard Webhooks checked against the reference vector and the official `standardwebhooks` library. See [dodo.md](dodo.md) | Digital products only: physical goods and manual or human-delivered services are not allowed by Dodo. Arbitrary amounts need a pay-what-you-want product in USD, GBP or EUR. A status lookup by `pay_` id alone is bound by metadata only: don't fulfil on it. The `refund_ref` check is per call, so two processes can both refund: run refunds from one place. Partial refunds of taxed payments are refused. Payouts are USD/GBP/EUR only and Dodo documents no FIRA. Checked against Dodo's docs and fixtures only: run one test-mode payment, refund and webhook before relying on it |
