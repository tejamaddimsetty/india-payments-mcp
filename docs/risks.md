# Risks, constraints and mitigations (deliverable L)

Likelihood (L) and impact (I) are rated H/M/L. Ordered roughly by L × I.

| # | Risk | L | I | Mitigation in place | Residual / what you should do |
|---|---|---|---|---|---|
| 1 | **Agent misuse: prompt injection triggers refunds or cancellations** | M | H | Live mutations are double-gated (`PAYMENTS_ALLOW_LIVE_MUTATIONS` + `confirm`). `destructiveHint` annotations. Tool descriptions demand human approval. Audit log records `blocked` attempts. `refund_ref` idempotency. Refunds bounded by the refundable balance | `confirm` can be set by the agent itself. Rely on MCP-client approval prompts. Never give an agent that reads untrusted text live refund rights. See [security.md §8](security.md#8-threat-model-for-agents) |
| 2 | **Gateway API drift** (field renames, new API versions, host moves) | H | M | Plain fetch with per-adapter contract tests. Pinned versions where the gateway supports it (Cashfree `x-api-version: 2026-01-01`, Stripe `2025-03-31.basil`). `lastVerified` date per capability map. `raw` passthrough. `api_drift` issue template | Drift appears as `PROVIDER_ERROR` / `SIGNATURE_INVALID` in production before tests catch it. Run a sandbox smoke test before upgrading, and monitor error rates per gateway |
| 3 | **Unverified CCAvenue details** (encryption kit, `orderStatusTracker` / `refundOrder` fields, API version 1.1 vs 1.2, no signed webhooks) | H | M | Marked `partial` / UNVERIFIED in capabilities and docs. Callbacks verified by decryption plus amount/order checks. Refunds never auto-retried | Test every CCAvenue flow in its sandbox. Confirm the kit (CBC vs GCM) with CCAvenue. Re-check status before fulfilling. Contributions with the official PDF are wanted |
| 4 | **Weakly authenticated webhooks** (PhonePe static auth header, CCAvenue decryption-only) | M | H | Both marked `partial`. Docs prescribe a status re-check in `onEvent` | Implement the re-check. The status API is the source of truth |
| 5 | **Per-process state** (idempotency store, webhook dedupe, MCP HTTP sessions, mock ledger) | H (when scaling) | M | Pluggable `IdempotencyStore`, `WebhookDedupeStore`, `AuditSink` interfaces. Gateway-side de-dupe ids where available | Before running more than one replica, plug in Redis/Postgres stores, use sticky sessions for `/mcp`, or run one replica. PayU/CCAvenue refunds have no gateway-side de-dupe |
| 6 | **"valid" misread as "paid"** | M | H | `valid` uniformly means "authentic and matches the order"; PaymentsClient adds `paid` (valid + captured/authorized). Docs say: fulfil only on `paid` | Razorpay `authorized` counts as paid; auto-capture must be on |
| 7 | **Stripe India is invite-only** | H | M | Capability summary and constraints say so. Recommender priors favour Stripe only for `international` | New Indian merchants generally can't onboard. Use Stripe as an exports adapter on existing accounts |
| 8 | **Skydo has no public API** | certain | L | Every feature is `unsupported` with guidance. `exporter_collections` recommendation | Don't build against claimed "Skydo APIs" without official confirmation. Pair Skydo invoicing with an API gateway |
| 9 | **Shopify limits**: Shopify Payments unavailable in India, payment extensions limited to approved partners | certain | M | Documented in the gateway matrix. Plugins listed per gateway | This project can't be a Shopify checkout. Use the gateway's Shopify app, and this server for status, refunds and recon |
| 10 | **Amount unit errors** (rupees vs paise) | M | H | Integer-paise-only API (`assertMinorUnits`, zod `int().positive()`). Adapters convert at the boundary. The PayU hash is computed over the exact sent string. Cashfree's rupees-as-number is converted both ways | Callers who pass rupees get a 100× **smaller** charge, not an error, if the value is an integer. Name variables `amountPaise` in your code |
| 11 | **Live key used in sandbox, or vice versa** | M | H | Razorpay prefix checks. `doctor` / `check_config` surface `initError` | PayU and CCAvenue keys aren't distinguishable. Keep sandbox and live secrets in separate vaults and processes |
| 12 | **Paytm host rebrand** (`securegw.paytm.in` → `secure(stage).paytmpayments.com`, refund pages showing `securegw-stage.paytmpayments.in`) | M | M | Defaults to the new hosts, documented in constraints | Confirm hosts in sandbox. Override via adapter changes if Paytm moves again |
| 13 | **PayU refund status and webhook formats only partly documented** | M | L | `partial`, defensive parsing, refund webhooks not parsed | Poll refund status |
| 14 | **Regulatory change** (RBI e-mandate thresholds, PA-PG, tokenisation, cross-border rules) | M | M | No card data handled. Hosted checkouts only. Constraints document current e-mandate rules | Not legal advice. Track RBI circulars and gateway notices. Thresholds in docs (₹15,000, 24 h pre-debit) may change |
| 15 | **Gateway outage** | M | M | Safe retries on reads. Typed `PROVIDER_UNAVAILABLE`. Recommender for alternatives | Checkout-level failover is your call. See the reliability playbook |
| 16 | **HTTP transport exposure** | L | H | Bearer token ≥ 24 chars, constant-time compare, loopback default, non-root container | No TLS, rate limiting or per-user auth built in. Put it behind a proxy |
| 17 | **Supply chain** | L | H | Two runtime deps (`@modelcontextprotocol/sdk`, `zod`). No gateway SDKs. Lockfile + `npm ci` in CI | Pin versions. Run `npm audit` / Dependabot. Verify npm provenance when you publish |
| 18 | **Generated integration code quality** | M | M | Generator emits server-side secrets only and verify-before-fulfil patterns | Review generated code like any PR |
| 19 | **Trademark / affiliation confusion** | L | M | Disclaimer in README and docs. No logos | Don't present this as an official SDK of any gateway |
